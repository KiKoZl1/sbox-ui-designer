# quest_journal

A centred, **RPG-style quest journal card** showcase for the SUI Designer.
Three tab buttons across the top (Active / Completed / Failed), a quest list
column on the left with three card slots, and a detail column on the right
showing the selected quest's title, long description, three objective rows
(label + progress bar each), and a reward line.

The sample is the showcase for the **runtime restyle via `Hud.View?.*` Panel
refs** pattern — six different buttons (3 tabs + 3 quest cards) are marked
"Expose as Variable" in the designer, which generates `@ref` fields on the
renderer so the controller can flip background colour, font colour, and font
weight to communicate selection state without bouncing through CSS classes or
authoring a state Variable per button. It also demonstrates the **single SUI
doc + many backing rows** pattern: the .sui only knows 10 Variables for "the
currently selected quest's fields", and the C# controller is free to swap
which quest is selected (via `PushSelectedQuest()`) without the document
having to model a `List<Quest>`. The wrapper class `QuestJournal` is
generated by the SUI Designer from `quest_journal.sui` on first compile, into
`Code/Samples/QuestJournal/` under the namespace `Sandbox.Samples`.

## What you'll see

A near-black scrim covers the screen. Centred on top sits a 1100 x 720
rounded card with a dark slate background and a 1px slate border. The title
"Quest Journal" sits in a bold 28px white line across the top, then three
tab buttons (Active / Completed / Failed) — Active is green-on-black, the
other two grey-on-slate by default. Below the tabs, the left column shows
three quest-card buttons stacked vertically with their titles; the first
card is darkened to indicate selection. The right column shows the selected
quest's title in 22px, a wrapped 14px slate description, then "OBJECTIVES"
as a tracked uppercase header followed by three rows of `label (progress
bar)` pairs. At the bottom of the right column, "REWARDS" sits above a
single line listing gold + items. Clicking any tab restyles the tab strip
green/grey and refreshes the quest list. Clicking any quest card restyles
the cards (selected = darker bg + white text) and rewrites the entire
detail column.

## How to use

1. **Drop the controller on any GameObject.** It's
   `Sandbox.Samples.QuestJournalController`. The default `ActiveQuests`,
   `CompletedQuests`, and `FailedQuests` lists produce a populated demo
   immediately — no inspector setup required.
2. **Hit Play.** The card mounts over a dim scrim — `Hud.Show( GameObject,
   SuiInputMode.MouseOnly )` in `OnStart` grabs mouse input for the buttons
   without stealing keyboard focus from gameplay.
3. **Click the Active / Completed / Failed tabs** to swap the seed quest set
   on the left. The controller restyles the tab strip in `RestyleTabs()`
   (green = active, grey = inactive) and rewrites the three quest-card
   labels in `PushQuestListLabels()`. Empty slots (e.g. Failed only has 1
   quest) render as a dim em-dash.
4. **Click any quest card** on the left to select it. The card restyles
   (darker bg + white bold text), the detail column rewrites, and the three
   objective progress bars animate to the selected quest's values.
5. **Press Tab** (`Score` action) to bump objective #1 of the selected quest
   forward by 10%. The bound `ProgressBar` value animates live — useful for
   verifying the binding pipeline without writing real quest-progress code.
6. **Press R** (`Reload` action) to reset every objective on the current
   tab's quest list back to zero. (Note: this resets to zero, not to the
   authored seed defaults — see the `ResetAllProgress` comment in the
   controller for why.)
7. **Reshape the demo from the inspector.** `ActiveQuests`, `CompletedQuests`,
   and `FailedQuests` are `[Property]` `List<Quest>` — edit them inline to
   change the quest titles, descriptions, rewards, and objective lists
   without touching code. Same pattern as `inventory_grid_full`.

## Variables

| Name | Type | Default | Role |
|---|---|---|---|
| `CurrentTabText` | `string` | `"Active"` | Which tab is currently shown — "Active" / "Completed" / "Failed". Controller writes `tab.ToString()` in `SwitchTab`. Available for any UI that wants to mirror the active tab label. |
| `SelectedQuestTitle` | `string` | `"Slay 10 Zombies"` | Title of the currently selected quest. OneWay-bound to `QuestTitleLabel`. Controller writes via `PushSelectedQuest()` after every selection change. |
| `SelectedQuestDescription` | `string` | `"Reports of zombie sightings near the village graveyard. Clear them out."` | Long-form description. OneWay-bound to `QuestDescriptionLabel`. |
| `Objective1Text` | `string` | `"Slay zombies (3/10)"` | Label of objective #1. Empty string leaves the row blank when the quest has fewer than 1 objective. |
| `Objective1Progress` | `float` | `0.3` | Progress 0..1 for objective #1. Bound to `Obj1Bar` (ProgressBar Min=0 Max=1). |
| `Objective2Text` | `string` | `"Return to Mayor"` | Label of objective #2. |
| `Objective2Progress` | `float` | `0` | Progress 0..1 for objective #2. |
| `Objective3Text` | `string` | `""` | Label of objective #3. Empty when the quest has fewer than 3 objectives. |
| `Objective3Progress` | `float` | `0` | Progress 0..1 for objective #3. |
| `SelectedQuestRewardText` | `string` | `"300 gold + Iron Sword"` | Gold + items the player earns on completion. OneWay-bound to `RewardLabel`. |

All ten live under the `Tabs` / `Detail` / `Objectives` / `Rewards` groups.
Controller pushes them via `PushSelectedQuest()` on every tab switch and
every quest selection. The data model (`Quest` and `Objective` POCOs) is
C#-only — `List<custom-POCO>` isn't a valid SUI Variable type, so the doc
just knows the "currently selected" projection and the controller maps the
selected index → those flat fields.

## Bindings

| Element | Property | Variable | Mode | Trigger |
|---|---|---|---|---|
| `QuestTitleLabel` (Text) | `Text` | `SelectedQuestTitle` | OneWay | OnChange |
| `QuestDescriptionLabel` (Text) | `Text` | `SelectedQuestDescription` | OneWay | OnChange |
| `Obj1Text` (Text) | `Text` | `Objective1Text` | OneWay | OnChange |
| `Obj1Bar` (ProgressBar) | `Value` | `Objective1Progress` | OneWay | OnChange |
| `Obj2Text` (Text) | `Text` | `Objective2Text` | OneWay | OnChange |
| `Obj2Bar` (ProgressBar) | `Value` | `Objective2Progress` | OneWay | OnChange |
| `Obj3Text` (Text) | `Text` | `Objective3Text` | OneWay | OnChange |
| `Obj3Bar` (ProgressBar) | `Value` | `Objective3Progress` | OneWay | OnChange |
| `RewardLabel` (Text) | `Text` | `SelectedQuestRewardText` | OneWay | OnChange |

Nine OneWay bindings cover the entire detail column. Notice what's **not**
bound: the three tab buttons' labels, the three quest-card buttons' labels,
the "OBJECTIVES" and "REWARDS" section headers, and `CurrentTabText`. The
tab and quest-card labels are mutated **inline** via `Hud.View?.QuestCard1
.ChildrenOfType<Label>().FirstOrDefault().Text = ...` in
`SetQuestCardText()` — the comment in the controller explains why
(authoring per-card text Variables would have meant 3 string Variables just
to label the 3 cards; the runtime mutation is shorter). The section headers
and `CurrentTabText` are display-only constants that never change.

## Events

| Element | Event | Mode | Handler | Wired via |
|---|---|---|---|---|
| `TabActive` (Button) | `OnClick` | Code | `OnTabActiveClick` | `Hud.OnTabActiveClick = OnTabActiveClick;` |
| `TabCompleted` (Button) | `OnClick` | Code | `OnTabCompletedClick` | `Hud.OnTabCompletedClick = OnTabCompletedClick;` |
| `TabFailed` (Button) | `OnClick` | Code | `OnTabFailedClick` | `Hud.OnTabFailedClick = OnTabFailedClick;` |
| `QuestCard1` (Button) | `OnClick` | Code | `OnQuest1Click` | `Hud.OnQuest1Click = OnQuest1Click;` |
| `QuestCard2` (Button) | `OnClick` | Code | `OnQuest2Click` | `Hud.OnQuest2Click = OnQuest2Click;` |
| `QuestCard3` (Button) | `OnClick` | Code | `OnQuest3Click` | `Hud.OnQuest3Click = OnQuest3Click;` |

Tab handlers call `SwitchTab(QuestTab)` which updates `_currentTab`,
rebuilds the quest list labels, re-pushes the selected quest, and restyles
both the tabs and the cards. Quest-card handlers call `SelectQuest(int)`
which updates `_selectedIndex`, re-pushes the selected quest, and restyles
the card column.

> WARNING — **Assign every Code-mode delegate BEFORE you call `Show(...)`.**
> All six `OnXxxClick` Actions must be on the wrapper **before** `Show()`
> runs — `Show()` triggers `SyncFieldsTo`, which copies the wrapper's
> Action delegates into the rendered Panel. Anything you assign **after**
> `Show()` lands on the wrapper but not on the live Panel — clicks silently
> no-op forever. Same gotcha that `counter_button`, `settings_full`, and
> `death_respawn_modal` document. The controller follows the rule:
>
> ```csharp
> Hud.OnTabActiveClick    = OnTabActiveClick;
> Hud.OnTabCompletedClick = OnTabCompletedClick;
> Hud.OnTabFailedClick    = OnTabFailedClick;
> Hud.OnQuest1Click       = OnQuest1Click;
> Hud.OnQuest2Click       = OnQuest2Click;
> Hud.OnQuest3Click       = OnQuest3Click;
> PushSelectedQuest();
> Hud.Show( GameObject, SuiInputMode.MouseOnly );
> ```

## Why six elements have `ExposeAsVariable = true`

The three tab buttons (`TabActive`, `TabCompleted`, `TabFailed`) and the
three quest-card buttons (`QuestCard1`, `QuestCard2`, `QuestCard3`) all
have **"Expose as Variable"** ticked in the Designer. That flag generates an
`@ref` field on the renderer Panel, surfaced to C# as `Hud.View?.TabActive`,
`Hud.View?.QuestCard1`, etc. The controller uses these refs to:

- **Restyle the active tab** (`RestyleTabs`) — `BackgroundColor`,
  `FontColor`, `FontWeight` switch between the authored "active" and
  "inactive" palettes when the user clicks a tab.
- **Restyle the selected quest card** (`RestyleQuestCards`) — same three
  style attributes flip on selection change.
- **Rewrite the quest-card label** (`SetQuestCardText`) — pulls the first
  `Label` child via `ChildrenOfType<Label>().FirstOrDefault()` and writes
  to its `Text` directly.

Without `ExposeAsVariable`, `Hud.View.TabActive` would be `null` and the
restyle methods would silently bail (the controller defensively null-checks
every access). Same `@ref` mechanism `boss_hp_bar` uses for `DamageFlash`,
just applied to six buttons instead of one overlay panel.

## Extending it

A few directions worth exploring once you've got it on screen:

1. **Hook to a real quest system.** Replace the three seed `[Property]`
   `List<Quest>` fields with a reference to your gameplay quest log
   (whatever stores active/completed/failed). Convert your quest records to
   the `Quest` POCO inside `OnStart` and keep them in sync via an event
   ("quest progress changed" → re-run `PushSelectedQuest()`). The wrapper
   stays untouched.
2. **Support more than three quests per tab.** The current design hard-codes
   3 card slots in the .sui. To scale, either (a) add more `QuestCardN`
   elements + `OnQuestNClick` handlers in the doc (works fine up to ~10), or
   (b) replace the static cards with a scrollable list — drop a Panel with
   `Overflow: Scroll`, generate cards dynamically in code via `View?.QuestList
   .AddChild( new Button { ... } )`, and assign click handlers per-card.
3. **Animate the progress bars.** When `PushSelectedQuest` writes a new
   `Objective1Progress` value, you currently snap to the new value. Wrap the
   push in a tween (lerp from old → new over 0.25s on `OnUpdate`) and the
   bars will sweep into place — same trick `boss_hp_bar` uses for the damage
   flash decay.
4. **Add a reward icon list.** The reward line is currently a single string
   ("300 gold + Iron Sword"). Replace `SelectedQuestRewardText` with a
   structured `List<RewardEntry>` (icon path + count), and render each entry
   as an `Image + Text` pair in a flex row. The reward header stays static;
   only the list row beneath it becomes dynamic.
5. **Persist selection across tab switches.** Currently `SwitchTab` resets
   `_selectedIndex` to 0. To remember "which card was last selected per
   tab", add a `Dictionary<QuestTab, int>` and snapshot the selection on
   tab change. Reapply when the tab is reselected.
6. **Show empty / completed states.** When `CurrentQuests.Count == 0`, the
   detail pane currently shows an em-dash and "No quest selected." Replace
   that with a custom empty-state Panel (badge + message + CTA) by setting
   the detail panel's `Visibility` and showing a sibling panel instead.
7. **Add a "track quest" toggle button.** Add a seventh button to the
   detail pane that adds the selected quest to an on-screen tracker HUD.
   Pair with a new SUI doc `tracked_quest_hud.sui` (small overlay in the
   top-right) that takes the same `SelectedQuestTitle` /
   `Objective1Progress` Variables. Two SUI docs sharing one controller as
   the bridge.

## File map

```
samples/showcase/quest_journal/
├── quest_journal.sui              — V3 document (24 elements, 10 variables, 6 Code-mode events)
├── QuestJournalController.cs      — Sandbox.Component, ~428 lines
├── build_sui.ps1                  — helper that rebuilds the .sui from a JSON definition
└── README.md                      — this file
```

On first compile inside an s&box project, the Designer's generator drops:

```
Code/Samples/QuestJournal/
├── QuestJournal.razor             — generated renderer (with 6 @ref fields)
├── QuestJournal.razor.scss        — generated styles
└── QuestJournal.cs                — generated wrapper (10 Variables, 6 Actions, View ref struct)
```

You only ever hand-edit `QuestJournalController.cs`. The three generated
files are regenerated from `quest_journal.sui` on every doc save and should
be treated as build output (don't commit edits to them — the Designer will
overwrite).
