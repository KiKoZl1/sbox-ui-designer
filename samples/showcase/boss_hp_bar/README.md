# boss_hp_bar

A dramatic, **Dark-Souls style centered boss HP bar** showcase for the SUI
Designer. Crimson fill, three phase divider ticks, an amber "Phase X/Y" caption
underneath, and a full-bar white damage flash that pulses on every hit.

The sample demonstrates four things at once:

- **OneWay bindings** driving a `ProgressBar` value and two `Text` strings from
  controller-side variables — no per-frame `Children[n].Style = ...` poking.
- **Layered `ZIndex` stacking** inside an Absolute-mode container, so the bar
  fill, the dividers, and the flash overlay paint in the right order without a
  flex layout.
- **An exposed-as-variable element** (`DamageFlash`) that the controller writes
  to directly via `Hud.View?.DamageFlash.Style.Opacity` — the escape hatch for
  effects that don't fit the binding model.
- **A live test harness** wired to two built-in actions (Tab to hit, R to heal)
  so you can verify the whole loop in 10 seconds without touching gameplay code.

The wrapper class `BossHpBar` is generated by the SUI Designer from
`boss_hp_bar.sui` on first compile, into `Code/Samples/BossHpBar/` under the
namespace `Sandbox.Samples`.

## What you'll see

A 1200 x 100 panel centered against the top of the screen, dark semi-transparent
backing, faint crimson outline. The boss name "ANCIENT DRAGON" sits in bold
tracked-out crimson caps at the top, then a 1152 x 24 horizontal HP bar fills
with crimson and empties left-to-right as the boss takes damage. Three black
divider ticks at 25 / 50 / 75 split the bar into four phases. An amber
"Phase X/4" caption sits below the bar, ticking up as the boss drops through
phases. Every time you press the hit hotkey, the bar flashes white from a 0.7
peak and decays back to invisible over roughly 0.2 seconds.

## How to use

1. **Drop the controller on any GameObject.** It's `Sandbox.Samples.BossHpBarController`.
   The default values produce a 5000 HP boss split into 4 phases.
2. **Hit Play.** The HUD appears immediately — `Hud.Show( SuiInputMode.Passive )`
   in `OnStart` makes it render-only so it never grabs your crosshair.
3. **Press Tab** (`Score` action) to deal 15% damage. The bar shrinks, the
   white overlay pulses, and the phase label updates when you cross a divider.
4. **Press R** (`Reload` action) to heal 10% back. No flash — heal is silent
   on purpose so it visually reads differently from damage.
5. **Inspect / tweak in the inspector.** All knobs are `[Property]` exposed:
   `BossName`, `CurrentHp`, `MaxHp`, `Phases`, `DamagePerHit`, `HealPerPress`,
   `FlashPeak`, `FlashDecayPerSecond`.

## Variables

| Name | Type | Default | Role |
|---|---|---|---|
| `BossName` | `string` | `"ANCIENT DRAGON"` | Display name. Controller uppercases the inspector value once in `OnStart`. |
| `HpFraction` | `float` | `1.0` | Normalized 0..1 health. Controller computes `CurrentHp / MaxHp` every tick. |
| `PhaseLabel` | `string` | `"Phase 1/4"` | Pre-formatted phase string. Controller computes from `ceil(HpFraction * Phases)`. |

## Bindings

| Element | Property | Variable | Mode | Trigger |
|---|---|---|---|---|
| `BossNameText` (Text) | `Text` | `BossName` | OneWay | OnChange |
| `HpBar` (ProgressBar) | `Value` | `HpFraction` | OneWay | OnChange |
| `PhaseLabel` (Text) | `Text` | `PhaseLabel` | OneWay | OnChange |

All three are OneWay because the HUD is read-only — the bar never gets dragged,
the labels never get edited inline. The matrix at
`Code/Runtime/SuiBindingModeMatrix.cs` confirms `ProgressBar.Value`, `Text.Text`
are all OneWay-capable; bindings are validated at load time so a typo here would
get flagged by `SuiDocumentValidator`.

## Events

This sample has **no Code-mode events**. Damage and heal are triggered by
polling `Input.Pressed( "Score" )` / `Input.Pressed( "Reload" )` from
`OnUpdate`, not from the UI itself. That keeps the HUD pure (no clickable
surface) and means the bar never has to compete with weapon fire for input
focus.

> ⚠️ **If you DO add Code-mode events later** (e.g. you wrap the bar in a
> Button to make it click-through for a debug menu): assign **all** Code-mode
> delegates on `Hud` *before* you call `Hud.Show(...)`. `Show` triggers a
> `SyncFieldsTo` pass that copies delegates into the renderer; anything you
> assign after `Show` lands on the wrapper but not on the live Panel.

## Element tree at a glance

```
root (Canvas, 1920x1080)
└── el_container (Panel, 1200x100, TopCenter pivot 0.5)
    ├── el_boss_name      (Text, ZIndex 1)         "ANCIENT DRAGON"
    ├── el_hp_track       (Panel, ZIndex 1)        dark slate backing
    ├── el_hp_bar         (ProgressBar, ZIndex 2)  crimson fill (binds Value)
    ├── el_tick_1         (Panel, ZIndex 3)        25% divider
    ├── el_tick_2         (Panel, ZIndex 3)        50% divider
    ├── el_tick_3         (Panel, ZIndex 3)        75% divider
    ├── el_phase_label    (Text, ZIndex 1)         "Phase X/4"
    └── el_damage_flash   (Panel, ZIndex 4)        white overlay, Opacity 0 → 0.7 → 0
```

Why so many ZIndex layers? Absolute-mode siblings paint in document order by
default, but I want the **ticks to stay visible over the bar fill** (so the
phases read at every HP level) and the **flash to sit on top of everything**.
ZIndex 1 → 2 → 3 → 4 spells out the stacking explicitly so a future rename or
reorder doesn't quietly break the silhouette.

## Why the `DamageFlash` overlay is `ExposeAsVariable = true`

The flash is the one element the controller writes to *directly* every tick
that has decay. Three reasons it doesn't go through a binding:

1. **There's no "Style.Opacity" bindable** in the matrix — opacity is a Panel
   style attribute, not a Variable-driven property. Bindings are for typed
   logical state (Value, Text, FillColor); transient render state stays on
   the Panel.
2. **The decay curve runs in `OnUpdate`** — making it a OneWay binding would
   mean writing the variable every frame, which churns the binding pipeline
   for a single Panel attribute. Direct write is cheaper.
3. **It needs to survive frame zero gracefully.** `Hud.View?.DamageFlash` is
   null until Razor mounts the renderer on the first render pass (same
   deferred-view gotcha that `inventory_grid_full` documents). The
   null-coalescing access pattern in `ApplyFlashOpacity` handles that
   without an explicit "wait for view" flag.

Generated as `@ref="DamageFlash"` on the renderer Panel — see
`Code/Generation/SuiElementRefEmitter.cs`. The field name comes from the
element's `Name` (sanitized to a C# identifier), not its `Id`.

## Extending it

A few directions worth exploring once you've got it on screen:

1. **Hook to real gameplay damage.** Replace the Input.Pressed hotkeys with a
   `[Broadcast]` RPC that fans out `TakeDamage` calls from any weapon hit. The
   controller becomes a pure receiver — drop one per boss spawn, wire the
   spawn flow to set `BossName` and `MaxHp` from the boss prefab data.
2. **Swap the visual style per phase.** In `PushToHud`, compare the new phase
   to the previous frame's phase; on a transition, change `HpBar`'s
   `ProgressFillColor` (crimson → purple → white-hot) by reaching for
   `Hud.View?.HpBar` (expose it too) and assigning the matching `ProgressBar`
   property at runtime, or rotate a CSS class via `AddClass / SetClass`.
3. **Add a screen-shake on damage.** Drive a `CameraComponent` from the same
   `TakeDamage` entry point — `GameObject.WorldTransform += Rotation.From(
   Random.Shared.Float(-1f, 1f), 0, 0 )` for one frame, lerp back over the
   flash decay window so the rumble matches the visual punch.
4. **Per-boss customization via a `[Resource]`.** Define a `BossDefinition`
   resource (`Name`, `MaxHp`, `Phases`, `FillColor`, `IconPath`) and have the
   controller read from it instead of inspector properties. Then the same
   wrapper renders any boss your designers configure without touching code.
5. **Animate the empty portion as "shield".** Stack a second `ProgressBar` on
   top of the HP bar at a lower ZIndex, bound to a separate `ShieldFraction`
   variable. Useful for bosses that regenerate or have armor layers — the
   shield bar drains first while the underlying HP bar holds.
